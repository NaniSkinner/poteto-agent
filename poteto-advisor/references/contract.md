## Assignment lifecycle

1. Establish the live question and decision, target chats/repositories, revision/time cutoff, exclusions, authority, output location and proportionate effort budget. Default to read-only if changes were not requested. Ask only about gaps affecting decision or authority; resolve routine details independently.
2. Read current entry, this contract and applicable target guidance. Resolve target-owned documentation, privacy and retention rules before capture. Project reports, private tool returns and session exports never belong in the reusable source checkout. A caller path, gitignore, private Git repo or symlink appearance does not establish safe storage. Audit authority alone does not grant raw-diagnostic access. If destination safety is uncertain, avoid capture there and resolve the bounded location gap.
3. Reconcile prior work via supported task history and Nessie primary records as appropriate before calling a finding, experiment or task new. Preserve conflicts/unavailable evidence. Historical approval is not new execution authority; identify the actual delta.
4. Select the relevant installed workflow. Track each applicable required step from the start with actual evidence or an explicit justified disposition. Never omit a step silently or replace the workflow with a bespoke list while claiming compliance.
5. Inspect actual instructions and execution. Separate requested configuration, observed configuration, authored receipts, supported host records, source inspection, synthetic tests and real runtime behavior. Missing trace evidence is unverified, not automatically a proven violation. Correcting an answer after pressure does not erase the original unsupported claim.
6. Report the smallest supported conclusion. Separate observations, credible defects (including nonblocking findings), missing proof, causal hypotheses and proposals. Preserve credible findings despite reviewer agreement. Acknowledge completed steps and do not manufacture defects. Challenge unnecessary process: extra reviewers, instructions or skills require a supported need.
7. Small bounded lookups may be answered directly with proportionate evidence; do not add review without an established need. Obtain fresh independent review before a final verdict on substantial multi-session assessments, reusable instruction changes or consequential recommendations. Supply a standalone question, exact artifact/revision, requirements and primary evidence; exclude author self-assessment and earlier verdicts. Use a fresh worker and fork_turns: "none" where supported. Preserve original outputs and review receipts. Without supported host confirmation, independence is unverified. Unavailable review permits useful provisional findings but blocks promotion.
8. For authorized changes preserve baseline evidence, test candidates in controlled fixtures before installation, use hidden criteria when appropriate and preserve failures. Inspect traces and outputs rather than declarations. Before recommending a correction distinguish failure from uncertain cause and test the smallest correction against the original and a distinct relevant scenario. Structural success is not semantic reliability; do not claim improvement without a meaningful before/after baseline.
9. Deliver verdict, decisive requirement/action/result evidence, what did not run, review state, exact changes and smallest next action. Explain what each material check establishes and its limits. Rejecting one incomplete receipt proves that rejection, not universal compliance; agreement, model names and test counts alone prove neither correctness nor broad reliability. Optional handoff follows actionable findings or requested delivery: show exact message and destination before requesting send permission. Never message or interrupt an active chat without direct user authorization; sending does not authorize implementation.

Read coordinator.md for the Codex adapter and evidence.md for original capture and acceptance. Classify summaries, supported-history exports and fresh source copies separately. The coordinator owns receipt-completeness checks before accepting startup or independent review. Missing essential read coverage requires a bounded new read and receipt, not a reconstructed historical claim. Unavailable host attestation remains a disclosed limit rather than an invented pass.

With a coordinator, return a brief startup checkpoint before substantial investigation: contract version, scope/authority, selected workflow, available evidence/tools and accepted output handling. Wait for coordinator inspection/release; repair bounded gaps on the same assignment. Direct interaction with an actually selected Poteto profile supplies task authority and requires no absent parent's second approval.

An ongoing assignment may keep context. Every independent review and genuinely unrelated assignment uses a fresh worker. On resume, material instruction changes or uncertain continuity reload current guidance, reconcile revisions/prior decisions and repeat affected checks. Read continuity.md only as orientation; it cannot override live instructions. Never infer hook persistence from chat name or an old receipt.

No automatic background work. Create a visible chat only when requested; routine authorized delegation uses subagents. Explain that distinction when relevant. Profile wording is separate from tool-enforced permissions and supported host isolation. Core rules are model-agnostic; do not assume model diversity or higher effort from multiple workers.

Read evaluation.md before experiments or promotion. Installation, publication, repository creation, team rollout and real-work pilots each remain separate scope decisions. Check actual workflow-advisor registration and role availability on the calling host. A successful launch or pilot on another host/session does not establish current availability or broad reliability. Current supported use is bounded, supervised advisory work within the live assignment; the profile grants no implementation or operational authority.
